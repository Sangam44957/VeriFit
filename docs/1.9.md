Verdict
Task 1.9: CHANGES REQUIRED

The objective says "comprehensive end-to-end tests,"

but much of the proposed suite is actually in-memory unit testing of JwtService and AuthorizationService.

That distinction matters.

1. The token-revocation tests are based on the old API
   This is the clearest blocker.

The document uses:

jwtService.createTokenMetadata(...)
and expects:

metadata.token
metadata.revokedAt
and explicitly says:

UPDATE auth_tokens SET revokedAt = NOW() WHERE token = ?

That directly contradicts the locked JWT contract.

Our accepted JWT implementation uses jti, not the raw token, for persistence/revocation. The 1.2 implementation explicitly changed token metadata to a jti-based record and removed raw-token persistence.

So this entire section must be rewritten around:

JWT
↓
verifyToken()
↓
payload.jti
↓
AuthRepository.findByJti()
↓
revokedAt
The 1.9 test must prove that behavior through the actual 1.8 repository/auth flow, not simulate revokedAt by mutating an in-memory object.

2. expect(true).toBe(true) is still present
   This was already prohibited in 1.8.

Task 1.9 still contains:

expect(true).toBe(true);
for multi-device behavior.

And again for JWT manipulation:

expect(true).toBe(true); // Handled by JwtService.verifyToken

Those are not tests.

Replace them with actual assertions against the system behavior.

3. The task claims E2E testing but doesn't actually test the API
   The objective says:

"comprehensive end-to-end tests covering all authentication flows"

But the proposed auth.flow.spec.ts mostly does:

new JwtService()
new OAuthService()
new AuthorizationService()
and calls them directly.

That doesn't test:

HTTP
↓
AuthGuard
↓
AuthController
↓
AuthService
↓
AuthRepository
↓
PostgreSQL
which is exactly what 1.8 just integrated.

A real 1.9 suite should test the boundaries introduced by 1.8.

4. OAuth tests don't test the actual OAuth callback
   The "Student Login → Access → Logout" scenario says:

OAuth callback (mocked)
and then jumps straight to:

jwtService.generateToken(...)

That's not testing the login flow.

The meaningful test should cover something like:

↓
state created
↓

↓
state consumed exactly once
↓
Google identity resolved by sub
↓
existing user resolved
↓
JWT generated
↓
jti persisted

↓
logout
↓
jti revoked
↓
same token rejected
Google HTTP calls can remain mocked, but your own application flow should execute for real.

5. The OAuth state test is probably using the wrong synchronous API
   The document does:

expect(() => oauthService.verifyOAuthState(state1)).not.toThrow();
and immediately reuses it.

But during 1.6 we changed OAuth state handling specifically so the state store can support the DB-backed implementation, and verifyOAuthState() became async.

Therefore 1.9 should not assume:

verifyOAuthState(...)
is synchronous.

The test must match the current contract, likely:

await oauthService.verifyOAuthState(...)
and verify single-use consumption using the real configured state store.

6. Account-lockout testing is conceptually stale
   Task 1.9 proposes:

Attempt 1-4 → increment
Attempt 5 → LOCKED

But our corrected 1.8 explicitly removed password-style lockout from the OAuth flow.

We should not reintroduce it simply because the old 1.9 document says so.

The correct test is the behavior that actually exists:

OAuth identity resolved
↓
User accountStatus
↓
ACTIVE → login allowed
LOCKED → login denied
SUSPENDED → login denied
That matches the established OAuth account-status model.

7. The authorization API is inconsistent inside this document
   One part calls:

authzService.canAccessResource(...)
while another calls:

authz.authorize(...)
For example the earlier flow uses canAccessResource, while the IDOR suite uses authorize.

That's a red flag.

Task 1.9 must use the actual current AuthorizationService API, not mix APIs from multiple historical versions.

8. "ADMIN has more permissions than STAFF" is the wrong invariant
   This test says:

expect(adminPerms.length).toBeGreaterThanOrEqual(staffPerms.length);
expect(staffPerms.length).toBeGreaterThanOrEqual(studentPerms.length);

That's exactly the kind of assumption we rejected earlier.

Our authorization model uses explicit permission policies, not a role hierarchy.

So the correct tests are:

ADMIN + permission X → allowed
STAFF + permission X → allowed/denied
STUDENT + permission X → denied
based on the actual policy matrix.

Never assert that one role must merely have a larger count than another.

9. The timing-attack test is meaningless and flaky
   This:

const timeDenied = Date.now() - startDenied;
const timeAllowed = Date.now() - startAllowed;

expect(Math.abs(timeDenied - timeAllowed)).toBeLessThan(100);

doesn't establish timing-attack resistance.

A scheduler can make either operation take longer.

This should be removed from 1.9.

Timing side-channel analysis is not something we can establish with two Date.now() calls in a Vitest unit test.

10. The SQL-injection test isn't testing SQL injection
    This test:

resourceId: "student-1'; DROP TABLE users;--"

expect(result.allowed).toBe(false);

No SQL query happens.

It only proves that a weird string doesn't satisfy an authorization condition.

Remove it from the security claims or replace it with a genuine repository/database parameterization test.

oauthService.generateAuthorizationUrl();

      expect(authorizationUrl).toContain('accounts.google.com');
      expect(state).toBeDefined();

      // Step 2: Student gets OAuth callback (mocked)
      // In real flow: Google redirects with code
      // Our code exchanges code for access_token
      // We get profile and lookup user

        email: studentOrg1.email,
        organizationId: studentOrg1.organizationId,
